## 2. 本番向け検討項目

優先度は、本番に出す前に必要な順。「決める」は保留事項（`HANDOFF.md` 第 7.4 章）で、ユーザーの判断が要る。

### 2.1 本番に出す前に必須（設定・コードの対応）

| # | 項目 | 現状 | 対応 | 関連 |
| --- | --- | --- | --- | --- |
| 1 | 本番用の設定ファイル | `application-prod.yml` が無い。今の設定で起動すると、H2 コンソール、動作確認用画面、Swagger、初期データがすべて有効になる | `application-prod.yml` を作る。`spring.flyway.locations` を `classpath:db/migration` のみ、H2 コンソールと Swagger を無効、`app.dev-ui.enabled=false`、ログを INFO | NFR-SEC-11、NFR-OPS |
| 2 | DB の認証情報 | `application.yml` に `sa/password`（H2 の開発用）が書いてある | 環境変数に替える。リポジトリに秘密を置かない | — |
| 3 | JWT 鍵 | 起動ごとに自動生成（再起動で全トークンが無効） | PEM ファイルかシークレット管理で固定し、定期的に更新する（`private-key-location`、`public-key-location`） | NFR-SEC-12 |
| 4 | 本番用 DB（PostgreSQL） | H2 のみで検証。型は PostgreSQL 互換で書いてある | JDBC ドライバ（`org.postgresql:postgresql`）と Flyway の PostgreSQL モジュールを追加（**依存の追加は要承認**）。CI のサービスコンテナで Flyway、検索、制約を検証 | ADR-0003 |
| 5 | HTTPS | 記載なし | 本番は HTTPS のみ。HSTS を有効にする。フロントエンドの Cookie は HTTPS で `Secure` が付く | NFR-SEC-10 |
| 6 | セキュリティヘッダー | Spring Security の既定のみ。CSP は無い | CSP、`X-Content-Type-Options` などを設計する（Next.js 側も） | — |
| 7 | 総当たり対策 | 回数制限・ロックなし | ログイン失敗の回数制限、ロック、通知 | NFR-SEC-06 |
| 8 | ログ | 個人情報、パスワード、トークンは出さない設計 | 本番のログレベル、保存先、保存期間を決める。監視を設計する | NFR-OPS-01、02 |

### 2.2 決める必要がある（保留事項。ユーザーの判断）

| # | 項目 | 内容 | 関連 |
| --- | --- | --- | --- |
| 9 | 自己登録の可否 | 現状は誰でも登録でき、USER 権限で全センターの更新・削除ができる。本番では管理者登録か承認制にするか | Q-1、NFR-SEC-05 |
| 10 | 権限（USER と ADMIN の差） | 現状は差が無い。誰が削除できるか、ADMIN の付与方法 | Q-2、NFR-SEC-04 |
| 11 | トークンの有効期限と失効 | アクセストークンは 15 分（変更しない方針）、リフレッシュは 7 日。**リフレッシュトークンを無効化できない**（ログアウトは画面側の Cookie 削除のみ。盗まれた場合は 7 日間有効）。失効の仕組み（ログアウト、無効化、ローテーション）を設計するか | NFR-SEC-02 |
| 12 | トークンの画面側の保管 | JavaScript から読める Cookie（原典を踏襲）。XSS でトークンを盗まれる。HttpOnly Cookie と BFF 方式への変更は設計変更 | NFR-SEC-03 |
| 13 | 在庫があるセンターの削除 | 禁止するか、警告のみか | Q-3 |
| 14 | 同時更新・同時登録 | 楽観ロック（`version` 列。スキーマ変更で要承認）。あわせて、カテゴリ名と在庫の名称の重複禁止は**アプリ層の事前照合だけ**で、同時リクエストで重複が通る余地がある（DB 制約は製品コードだけ）。対策案は `detailed-design-stocks.md` 第 6.1 章 | NFR-SEC-14、M-2 |
| 15 | 個人情報の方針 | 氏名、メール、管理者名、電話番号の保存期間と削除 | NFR-SEC-09 |

### 2.3 機能・データの検討（本番の要否は未定）

| # | 項目 | 内容 |
| --- | --- | --- |
| 16 | センターの詳細画面 | 一覧の行から全項目と在庫（部品・製品）を表示する。既存の `center_id` の外部キーで実現できる（読み取りの API を追加するだけでよい） |
| 17 | 連絡事項（お知らせ・申し送り） | センターごとに日付付きで複数件を持つ。`center_info.notes`（255 文字、1 件）では足りないため、`center_id` を外部キーにした子テーブルが必要（スキーマ変更で要承認）。要件（誰が書くか、件数、既読）が未定義 |
| 18 | 操作履歴 | 誰がいつ何を変えたか。要件が未定義 |

| 20 | 区分・状態のデータ | 稼働状況と削除フラグは各テーブルの `SMALLINT` と CHECK。カテゴリ種別は `category_info` の列（`part`/`product`）。値が増えて画面で管理したくなったら、区分テーブル（マスタ）に切り出す。部品在庫と製品在庫を 1 つにまとめる案は、原典の定義からの変更になる |

## 3. 進め方の提案

1. 本番に出す予定が決まった時点で、第 2.1 章の 1〜3（本番用設定、DB 認証情報、JWT 鍵）から着手する。コードの変更が小さく、効果が大きい。
2. 第 2.2 章の判断（9、10、11）は、運用の想定が決まってから行う。
3. 第 2.3 章の機能は、要件を決めてから設計する（スキーマ変更と API 契約の変更は承認が必要）。
