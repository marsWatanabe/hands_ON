## 1. 総評

- 仕様書にある 4 API と認証は動作し、統合テスト 12 件が通っている。バリデーション、論理削除、ページング、エラー形式は仕様どおり。
- 一方、**業務アプリとして使うには、API の外側が未整備**。要件定義と基本設計が無いまま、実装者が仮置きした判断が多い（第 5 章）。
- 優先して決めるべきこと: **誰がアカウントを作れるか**、**センター削除時の扱い**、**現在保存容量の更新元**、**フロントエンドの接続方法**。

重大度の基準: **High** = 本番運用前に必須、**Medium** = 業務上の不具合や手戻りにつながる、**Low** = 品質向上。

## 2. 確認できた事実（実測）

| 確認 | 結果 |
| --- | --- |
| `mvnw test` | 12 件成功（認証、検索、ソート、ページング、入力エラー、作成・更新・論理削除） |
| 認証なしで `GET /centers` | 401（共通エラー形式） |
| リフレッシュトークンで `GET /centers` | 403 |
| `/v3/api-docs` の `CenterRequest` | 入力項目に **`capacityConsistent` が混入**している（指摘 L-1） |
| 別オリジン（`http://localhost:3000`）からの CORS プリフライト | **403 で拒否**される（指摘 H-2） |

## 3. 指摘事項

### High

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| H-1 | セキュリティ（要確認） | `POST /auth/register` が**誰でも**呼べ、登録直後に USER 権限で在庫センターを操作できる。**原典の設計でも同じ**（登録画面あり、README も登録を案内）。研修ではこれでよいが、業務利用では第三者が自己登録してデータを操作できる状態になる。 | `SecurityConfig`、`AuthenticationService.register` | 本番の登録方針（管理者登録、承認制、SSO）を決める（R-1、Q-1） |
| H-2 | 連携（訂正: Low） | CORS 設定が無く、別オリジンのフロントから直接は呼べない（実測で 403）。ただし原典の画面は Next.js の `rewrites`（`/api/*` をバックエンドへ転送）で呼ぶため、**現構成では問題にならない**。 | `SecurityConfig`（`cors(withDefaults())` のみ） | 画面からバックエンドを直接呼ぶ構成にする場合のみ、許可オリジンを設定する |
| H-3 | 運用 | 本番用の設定が無い。H2 インメモリ、`ddl-auto: update`、起動ごとに変わる JWT 鍵、サンプルデータ自動投入、Swagger が未認証で公開、という開発用のまま。 | `application.yml`、`SecurityConfig` | `prod` プロファイルを分け、DB 本体、Flyway 等のマイグレーション、固定鍵、Swagger の無効化または認証付きにする |
| H-4 | 業務ルール | センター削除時に、このセンターを参照する在庫（原典の `parts_stock_info`、`products_stock_info` の `center_id`）があるかを確認していない。論理削除のため、削除済みセンターを参照する在庫行が残る。 | `InventoryCenterService.delete` | 在庫があるセンターの削除可否を決めて実装する（R-3、要件定義書 Q-3） |
| H-5 | 原典との不一致（**新規**） | 原典は「`table-definitions.md` が唯一の真実」とし、テーブル名 `center_info`、列の桁数と NOT NULL、Flyway を定めている。hands_ON はテーブル名 `inventory_center`、異なる桁数、`ddl-auto=update`、英語のメッセージ、異なるエラーコード、フラットなパッケージであり、**後続の画面・在庫 API とつながらない**。 | `InventoryCenter`、`application.yml`、`GlobalExceptionHandler` | 原典に合わせて修正する。差分は[詳細設計書](../detailed-design.md)第 8 章、[ER 図](../er-diagram.md)第 7 章 |

### Medium

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| M-1 | 整合性 | `currentStorageCapacity`（現在保存容量）が**手入力で更新できる**。原典の在庫テーブルは数量（個）しか持たず、品目ごとの体積（m³）が無いため、**在庫から算出できない**。誰でも任意の値に書き換えられる。 | `CenterRequest`、`InventoryCenterService.apply` | 現在保管容量の更新元を要件で決める（要件定義書 Q-4） |
| M-2 | 同時更新 | 楽観ロック（バージョン列）が無く、**同時編集の後勝ち**で更新が失われる。 | `InventoryCenter` | `@Version` を追加し、競合時は 409 を返す |
| M-3 | 監査 | 作成者、更新者、変更履歴が残らない。業務アプリでは「誰がいつ変更したか」が必要になることが多い。 | `InventoryCenter` | `createdBy`、`updatedBy` を追加、または履歴テーブルを作る（R-6） |
| M-4 | 画面連携 | 入力エラーが `message` の**1 本の文字列**で、項目単位のエラーを画面に出しにくい。英語のメッセージのままで、画面は日本語想定。 | `GlobalExceptionHandler.describe` | `error.details: [{field, message}]` を追加し、日本語メッセージに対応する |
| M-5 | 業務ルール | センター名の一意性が**削除済みを含む**ため、削除したセンターの名前を再利用できない。 | `InventoryCenterRepository.existsByCenterName` | 要件で決める（R-4）。再利用可にするなら、ユニーク制約を「未削除のみ」にする |
| M-6 | セキュリティ | ログイン失敗の回数制限やロックが無く、総当たりを防げない。リフレッシュトークンの失効（ログアウト、無効化）も無い。無効化したユーザーの扱いもできない。 | `AuthenticationService` | 試行回数の制限、ユーザーの有効/無効フラグ、トークン失効の方式を決める（R-1） |
| M-7 | 権限 | USER と ADMIN の区別が、`/users/{id}` 以外にほぼ無い。USER がセンターを削除できてよいか不明。 | `SecurityConfig` | 操作ごとの権限表を作る（R-2） |
| M-8 | テスト | **ユニットテストが無い**（統合テストのみ）。スライドの成果物はフロントとバックにユニットテストを含む。サービス層の分岐（重複、404、並び順の安定化）を単体で確認していない。 | `src/test` | `InventoryCenterService`、`JwtService` のユニットテストを追加 |
| M-9 | DB 依存 | 検索は `lower(col) like '%x%'`。H2 では動くが、**本番 DB の種類が未定**で、照合順序と ESCAPE の挙動が DB で異なる。インデックスも効かない。 | `InventoryCenterService.contains` | 本番 DB を決め、同じ DB で検索テストを行う。件数が増えるなら全文検索を検討する |

### Low

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| L-1 | API 仕様 | `isCapacityConsistent()` が OpenAPI の入力項目 `capacityConsistent` として出てしまう（実測）。 | `CenterRequest` | `@JsonIgnore`（または `@Schema(hidden = true)`）を付ける |
| L-2 | 仕様差異 | `GET /users/{id}` は「本人または ADMIN」に限定した。仕様書は「認証必須」のみで、**意図的な差異**。 | `UserController` | 仕様書側を更新する |
| L-3 | 仕様差異 | 作成の成功は 200（仕様書どおり）。REST の慣例は 201 Created。 | `InventoryCenterController` | 方針を決めて仕様書に明記する |
| L-4 | 入力 | 郵便番号と電話番号は日本国内の形式のみ。海外拠点を持つ場合は対応できない。空文字は許可している。 | `CenterRequest` | 要件で対象範囲を確認する |
| L-5 | 日時 | `LocalDateTime` でタイムゾーン情報が無く、JVM の設定に依存する。 | `InventoryCenter`、`CenterResponse` | 運用タイムゾーンを決める（UTC 保存か JST 固定か） |
| L-6 | 可観測性 | リクエストログ、相関 ID、監査ログが無い。 | 全体 | アクセスログとトレース ID を追加する |
| L-7 | 範囲外ページ | 総ページ数を超える `page` は 200 で空の `data` を返す。`totalPages` は 0 件のとき 0。 | `PageResponse` | 仕様書に挙動を明記する |

## 4. 観点別の結論

| 観点 | 評価 | 備考 |
| --- | --- | --- |
| 実装可能性 | 良 | 仕様どおり動作 |
| セキュリティ（実装内） | 良 | SQL インジェクション対策、LIKE のエスケープ、パスワードのハッシュ化、IDOR 対策、リフレッシュ/アクセストークンの分離 |
| セキュリティ（運用） | 要改善 | H-1、H-3、M-6 |
| パフォーマンス | 現状問題なし | 件数が増える場合は M-9 |
| 保守性 | 良 | レイヤー分離、共通例外処理 |
| 業務適合 | **要確認** | 要件の未確定事項が多い（第 5 章） |

## 5. 業務アプリとして必要な要件定義・基本設計

現状は、仕様書の「API インタフェース仕様」だけで実装している。業務アプリにするには、次の資料が必要。**R-1 から R-4 は、確定しないと実装をやり直す可能性が高い。**

### 5.1 要件定義で決めること

| ID | 論点 | 確認したい内容 | 影響する指摘 |
| --- | --- | --- | --- |
| R-1 | 利用者とアカウント管理 | 誰が使うか（社内のみか、拠点ごとか）。アカウントは誰がどう作るか（自己登録、管理者登録、SSO）。ログアウト、アカウント停止、パスワード再設定は必要か | H-1、M-6 |
| R-2 | 権限モデル | 役割の種類（閲覧のみ、拠点担当、管理者など）。操作ごとの可否（作成、更新、削除） | M-7 |
| R-3 | 在庫との関係 | 在庫センターと部品・製品在庫の関係。現在保存容量は何から決まるか。センター削除時に在庫があればどうするか。容量の単位は何か | H-4、M-1 |
| R-4 | センターのルール | センター名の重複と再利用。稼働状況の変更条件（停止中は入出庫不可など）。必須項目（郵便番号、住所、電話番号） | M-5、L-4 |
| R-5 | 非機能要件 | 利用者数、データ件数、可用性、バックアップ、応答時間、監視、保管期間、利用可能な DB | H-3、M-9 |
| R-6 | 監査・法令 | 変更履歴の要否、保存期間、個人情報（管理者名、電話番号）の取り扱い | M-3 |

### 5.2 基本設計で作る資料

| 資料 | 内容 | 現状 |
| --- | --- | --- |
| 画面仕様書（在庫センター情報画面） | 原典の `docs/screen-specifications.md` に**ある**。検索バー、テーブル列、フォーム、操作フロー。ただし原典内に不整合がある（要件定義書第 7 章） | 要修正（原典と hands_ON で項目が食い違う点を整理済み） |
| 画面遷移図 | ログインから一覧、詳細・編集までの遷移 | 未作成 |
| データ設計（ER 図、テーブル定義） | `inventory_center`、`users`、将来の在庫テーブル。インデックス、制約、文字数 | 一部のみ（コードから逆算） |
| 権限設計 | 役割と操作の対応表 | 未作成 |
| エラーとメッセージ設計 | エラーコード一覧、日本語メッセージ、項目単位のエラー形式 | 部分的 |
| 非機能設計 | 環境構成、設定の分離、鍵管理、ログと監視、バックアップ | 未作成 |
| テスト方針 | 単体、結合、受け入れの範囲。テストデータ | 結合テストのみ |
| API 仕様書の更新 | L-2、L-3、L-7 の差異反映。エラーレスポンス例の追加 | 一部差異あり |

## 6. 次のアクション（提案）

1. 第 5.1 章の R-1 から R-4 を、利用部門または担当者に確認する。
2. 確認結果をもとに、画面仕様書と権限表を作る。
3. 要件に依存しない修正を先に行う: H-2（CORS）、L-1（`capacityConsistent` の除外）、M-2（楽観ロック）、M-4（項目別エラー）、M-8（ユニットテスト）。
4. 別のモデルで同じレビューを行い、指摘の違いを比較する（スライド IV-1 と IV-2）。
5. 修正後に、本書の指摘をクローズする。
