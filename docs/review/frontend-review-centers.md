## 1. 総評

- 設計書どおりの画面（一覧、検索、並び替え、ページ送り、登録、編集、削除）が動き、自動テストで裏付けられている。
- ロジックを `lib/`（住所、入力検証、API 呼び出し、トークン更新）の純粋な関数に分け、単体テストを付けている点は良い。
- 本番に出す前に決めるべきことは、**トークンの保存方法（High）**。そのほかは、UI の改修（画面の幅、エラー表示）と CI の整備が中心。

## 3. Day3 の実装ステップとの対応

Day3 の例（在庫センター情報取得）のステップが、どのファイルに当たるか。

| ステップ | 実装 |
| --- | --- |
| Step1 型定義 | `app/types/api.ts` |
| Step2 API 呼び出しロジック | `app/lib/api-client.ts`、`centers-api.ts`（カテゴリ・在庫は `categories-api.ts`、`stocks-api.ts`）、`hooks/useCenters.ts`、`hooks/usePagedList.ts` |

| Step4 テーブル | `app/centers/_components/CenterTable.tsx`（同 `CategoryTable.tsx`、`stocks/StockTable.tsx`） |

## 4. 指摘事項

### High

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| FH-1 | セキュリティ（既知） | アクセストークン（保持 1 日）、リフレッシュトークン（保持 7 日）、ユーザー情報（氏名、メール）を、JavaScript から読める Cookie に保存している（原典を踏襲。NFR-SEC-03）。XSS が起きるとトークンを盗まれる。`SameSite=Strict` と、HTTPS での `Secure` は付けている。 | `lib/auth-storage.ts` | HttpOnly Cookie と、Next.js のサーバーを経由する方式（BFF）に変える。設計変更のため要承認 |

### Medium

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| FM-1 | 画面（実測） | 幅 1600px 未満で、在庫センター管理の一覧の右端の操作列（編集・削除）が見えない。幅 1366〜1536px のノート PC で多い。部品在庫は 1440px 未満、製品在庫は 1536px 未満でも横スクロールする（カテゴリは 1280px でも収まる）。 | `CenterTable.tsx`、`StockTable.tsx` | UI 改修で、操作列の固定（sticky）、列幅、折り返しを検討する |
| FM-2 | 保守性 | エラーを表示する項目の推定が、サーバーのメッセージ文字列に依存している（`guessStockErrorField`、`conflictFieldOf`、在庫センターの 400）。文言が変わると効かない。DB の制約で競合が起きたときの汎用メッセージは、製品コードの衝突でも名称欄に表示される。 | `lib/stock-form.ts`、`CenterFormModal.tsx` | API に項目別のエラー（`error.details`）を足す。API 契約の変更のため要承認 |
| FM-3 | 信頼性 | `apiFetch` にタイムアウトや中断がない。サーバーが応答しないと、一覧が「読み込み中」のままになる。 | `lib/api-client.ts` | `AbortController` とタイムアウトを追加する |
| FM-4 | テスト | E2E テストが CI で実行されていない（ローカルのみ）。回帰をローカルでしか検知できない。 | `.github/workflows/ci.yml` | CI でバックエンドを起動し、Playwright を実行する |
| FM-5 | セキュリティ（バックエンド側の既知事項） | ログアウトはブラウザの Cookie の削除だけで、サーバー側でトークンを無効化できない（盗まれた場合、リフレッシュトークンは 7 日間有効）。 | `AuthContext.tsx`（バックエンドに失効 API が無い） | 失効の仕組みを設計する（HANDOFF 7.4 の保留事項） |

### Low

| ID | 観点 | 指摘 | 場所 | 推奨 |
| --- | --- | --- | --- | --- |
| FL-1 | 整合 | アクセストークンの Cookie の保持（1 日）が、サーバー側の有効期限（15 分）と一致しない。期限切れのたびに 401、更新、再試行の往復になる（動作は正しい）。 | `lib/auth-storage.ts` | 有効期限の方針が決まったら合わせる |
| FL-2 | 堅牢性 | 2xx では常に `res.json()` を呼ぶ。本文のない応答（204 など）の API を追加すると例外になる（現在の API はすべて JSON を返す）。 | `lib/api-client.ts` | 本文なしの応答を扱えるようにする |
| FL-3 | 開発体験 | 開発サーバーの起動直後の初回アクセスで、画面の部品の読み込みに失敗することがある（再読み込みで直る。本番ビルドでは起きない）。 | Next.js の開発サーバー | README に注意を書く |
| FL-4 | 依存 | Next.js 15.5.6 は最新ではない（開発画面に表示される）。依存の脆弱性検査（`npm audit`、Dependabot）は CI に未導入。 | `package.json` | 更新方針を決め、検査を CI に入れる（本番向け検討項目 22） |
| FL-5 | 画面 | 住所の分割は規則による推定で、誤分割しうる（設計書第 4 章の既知の限界）。 | `lib/address.ts` | 列を分ける（要承認）か、住所の辞書を使う |
| FL-6 | 範囲 | ダッシュボード、操作履歴、アカウントの各画面は未実装（要件が未定義）。 | — | 要件を決めてから作る |
| FL-7 | 同時編集 | 同じ行を 2 人が編集すると、後の保存が先を上書きする（楽観ロックなし）。 | API 契約全体 | `version` 列の追加（API 契約の変更。画面の改修前に決めるのが安い） |

## 5. 観点別の結論

| 観点 | 評価 | 備考 |
| --- | --- | --- |
| 設計との一致 | 良 | 画面、列、検索条件、メッセージが設計書どおり |
| 実装の構造 | 良 | ロジックを `lib/` の純粋な関数に分離。一覧は `usePagedList` に共通化し、古い応答を破棄する |
| 入力検証 | 良 | 画面とバックエンドで同じ規則。サーバー側の検証が正 |
| 認証 | 要改善（FH-1、FM-5） | トークンの保存と失効 |
| アクセシビリティ | 概ね良 | 見出しに `aria-sort`、操作ボタンに「名称（センター名）を編集」のラベル、検索は `role=search` |
| 画面の幅（レスポンシブ） | 要改善（FM-1） | 実測あり |
| テスト | 良（CI 未実行は FM-4） | 単体 109 件、E2E 46 件、画面の通し 50 操作 |
| 本番ビルド | 良 | `next build` 成功 |

## 6. 次のアクション（提案）

1. FH-1（トークンの保存）の方針を決める。BFF 方式にするか、現状のまま運用範囲を限定するか。
2. 画面の改修（UI/UX）に合わせて、FM-1（操作列）、FM-3（タイムアウト）を対応する。
3. FM-2 と FL-7 は API 契約の変更になるため、改修前にまとめて決める（`error.details`、`version`）。
4. FM-4（E2E の CI 化）は、バックエンドの PostgreSQL 検証（HANDOFF 7.2）と一緒に進める。
5. 別のモデルで同じ観点のレビューを行い、指摘の違いを比較する。
