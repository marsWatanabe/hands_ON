## 1. 確認の方法

- **方法**: サンプルの指摘とシナリオを、現在のコードに当てはめた。挙動が不明な点は、**一時的な確認用テスト**（`TmpReviewProbeTest`）を書いて実際に呼び出した。
- **一時的なテストの扱い**: 実行後に削除済みで、リポジトリには残っていない。結果は第 3 章に記録した。
- **実行環境**: JDK 26（ビルドは Java 21 向け）、Spring Boot 3.5.6、プロファイル `test`（インメモリ H2）。初期データは在庫センター 3 件（東京、大阪、名古屋。すべて稼働中）。
- **呼び出し方**: ユーザーを登録してアクセストークンを取得し、`MockMvc` で `GET /api/v1/centers` を呼んだ（実際のセキュリティ設定と DB を通る）。
- **範囲**: 一覧取得の API が対象。作成・更新・削除は今回の確認の対象外。

## 3. 確認テストの結果

### 3.1 ページングの境界

| # | リクエスト | 結果 | 判定 |
| --- | --- | --- | --- |
| 1 | `page=21474837&size=100` | 200。`data` は空、`meta.total=3`、`meta.page=21474837`、`meta.totalPages=1` | 問題なし |
| 2 | `page=21474838&size=100` | **500 `INTERNAL_ERROR`**（「サーバー内部でエラーが発生しました。」） | **問題あり（M4）** |
| 3 | `page=2147483647&size=1` | 200。`data` は空、`meta.total=3`、`meta.totalPages=3` | 問題なし |

- #2 のオフセットは $(21474838 - 1) \times 100 = 2147483700$ で、`Integer.MAX_VALUE`（2147483647）を超える。
- `page` は「1 以上」、`size` は「1 以上 100 以下」という API 仕様の範囲内の入力なので、400 ではなく空の一覧を返すべき。
- #1 と #2 の境界は、オフセットが `int` に収まるかどうかで決まる。

### 3.2 空の結果

| # | リクエスト | 結果 | 判定 |
| --- | --- | --- | --- |
| 4 | `centerName=存在しない名前` | 200。`data` は空、`meta.total=0`、**`meta.totalPages=0`** | 要確認（C-2） |

- サンプルのレビューは、回帰シナリオに「空結果の `totalPages=1`」を挙げている。API 仕様書にはこの値の定義が無い（例は 5 件で `totalPages=1`）。

### 3.3 入力検証

| # | リクエスト | 結果 | 判定 |
| --- | --- | --- | --- |
| 5 | `centerName` = 空白 2 文字 + 20 文字（計 22 文字） | **400 `VALIDATION_ERROR`**（「センター名は20文字以内で入力してください」） | 要確認（C-3） |
| 6 | `centerName` = 21 文字 | 400 `VALIDATION_ERROR` | 問題なし |
| 7 | `page=abc` | 400 `VALIDATION_ERROR`（「page: 形式が不正です」） | 問題なし |

- #5 は、サンプルの実装では「検証の前に文字列を正規化（前後の空白を除去）する」ため 200 になる。こちらは**検証してから**検索時に空白を除去する。そのため、空白を除くと 20 文字でも、入力のままでは 20 文字を超えると 400 になる。

### 3.4 ソート（8 項目の昇順、`size=1`）

| # | `sort`（`order=asc`） | ステータス | 先頭の行 |
| --- | --- | --- | --- |
| 8 | `centerId` | 200 | 東京センター（ID 1） |
| 9 | `centerName` | 200 | 名古屋センター |
| 10 | `address` | 200 | 大阪センター |
| 11 | `operationalStatus` | 200 | 東京センター（同値のため ID の昇順） |
| 12 | `maxStorageCapacity` | 200 | 名古屋センター（6000） |
| 13 | `currentStorageCapacity` | 200 | 名古屋センター（1900） |
| 14 | `createDate` | 200 | 東京センター（同値のため ID の昇順） |
| 15 | `updateDate` | 200 | 東京センター（同値のため ID の昇順） |

- 仕様の 8 項目すべてが 200 で、先頭の行は、文字コード順（名 < 大 < 東、愛 > 大）と容量の昇順に一致した。
- ただし確認したのは先頭の 1 行だけで、全行の並び順までは検証していない。

### 3.5 ページ間の順序

| # | リクエスト | 先頭の行 |
| --- | --- | --- |
| 16 | `page=1&size=2&sort=operationalStatus&order=asc` | 東京センター（ID 1） |
| 17 | `page=2&size=2&sort=operationalStatus&order=asc` | 名古屋センター（ID 3） |

- 稼働状況がすべて同じ値でも、第 2 ソートキー（ID の昇順）により、ページ間で重複も欠落もなかった（1 ページ目が ID 1、2、2 ページ目が ID 3）。確認したのは各ページの先頭の行のみ。

## 4. サンプルのレビューとの比較

| 観点 | サンプルの結果 | こちら | 判定 |
| --- | --- | --- | --- |
| M4: 大きいページ番号で 500 | 指摘あり（対応済み） | **同じ問題あり** | 要対応 |
| 未削除の条件、AND の結合、`%` `_` `\` のエスケープ | 良い点 | 実装済み。テストもある | 同等 |
| ソート 8 項目と ID の第 2 キー | 良い点（固定マッピング） | 許可リストで検証し、第 2 キーあり | 同等 |
| 型変換エラーの 400 | 経路を確認 | 400 の共通形式 | 同等 |
| 認可（USER / ADMIN） | メソッド認可 + 既存の変換 | URL 単位の認可（`hasAnyRole`）。メソッド認可は無い | 差あり（下記） |
| 401 の応答 | 空の本文（承認済みの例外） | JSON の共通エラー形式（`AUTH_ERROR`） | 方針の違い。対応不要 |
| 検証と正規化の順序 | 正規化してから検証 | 検証してから正規化 | 要確認 |
| 空結果の `totalPages` | 1 を期待するシナリオ | 0 | 要確認 |
| L4: テストの不足 | 指摘あり | 一部が不足（第 5 章 D） | 要対応 |

- **認可の差**: こちらは URL 単位の `hasAnyRole` で、動作に問題はない。メソッド単位（`@PreAuthorize`）の認可は追加していない。必須ではなく、二重の防御として検討できる程度。

## 5. 要対応項目

優先度は、**高** = 次に直す、**中** = 方針を決めて対応、**低** = 余裕があれば対応。

| ID | 優先度 | 内容 | 対応案 | 承認・判断 |
| --- | --- | --- | --- | --- |
| **A（M4）** | **高** | `page=21474838&size=100` で 500（第 3.1 章 #2）。Spring Data JPA が、`int` を超えるオフセットを例外にするため | `CenterService.search` で、オフセット（`(page-1) × size`）が `Integer.MAX_VALUE` を超えるときは検索を実行せず、同じ条件で総件数だけ取得して空の一覧を返す（サンプルの対応と同じ）。400 にする場合は入力制約の追加になり、API 契約の変更として承認が必要 | 空の一覧を返す方針なら承認は不要。400 にするなら要承認 |
| B（C-2） | 中 | 空の結果の `totalPages` が 0（#4） | 仕様書に値を明記する。サンプルに合わせるなら 1（`Math.max(1, totalPages)`）に変更。**API 仕様の解釈なので、先に決める** | **要判断** |
| C（C-3） | 中 | 前後の空白の扱い（#5）。検証前に正規化するかどうか | 検証前にトリムするなら、`CenterSearchRequest` の setter でトリムする（空文字は `null` 扱い）。画面側の入力と合わせる | **要判断** |
| D（L4） | 中 | 自動テストの不足。サンプルの回帰シナリオのうち、次の 3 つが無い | 下の D の表のテストを追加する | A と B・C の決定後 |
| E | 低 | 作業ツリーの未コミットの変更。`SecurityConfig.java` と `DatabaseSchemaTest.java` の import の並び順、追跡されている `.LCKUser.java~`（エディタのロックファイル）2 件の削除 | `.gitignore` に `.LCK*~` を追加し、削除と合わせてコミットする。import の並びは、プロジェクトの規約（Google Java Style）に合わせるか決める | あなたの編集のため、確認してからコミット |
| F | 低 | CI の通知への対応。`actions/setup-java@v4` が非推奨（`@v5` へ）、`ubuntu-latest` が 2026-10-19 から Ubuntu 26 に切り替わる | `ci.yml` と `copilot-setup-steps.yml` を `setup-java@v5` に更新し、CI を再実行して成功を確認する | 不要 |
| G | 低 | 認可の二重化（メソッド単位）。第 4 章の差 | 必要性を検討する | 要判断 |

### D: 追加するテスト（案）

| 対象 | シナリオ | 期待 | テストの種類 |
| --- | --- | --- | --- |
| ページング | `size=100` で `page=21474837` と `page=21474838`、`page=Integer.MAX_VALUE` | すべて 200 で空の一覧。`meta.total` は実際の件数 | 結合（Service の単体テストも） |
| 空の結果 | 該当なしの検索 | `meta.total=0`。`totalPages` は B の決定に従う | 結合 |
| 並び順 | 8 項目それぞれで昇順・降順 | 全行が期待する順序になる（先頭だけでなく全行） | Repository（H2） |
| ページ間 | 同値の多いデータで、ページを順に取得 | 重複も欠落もない | Repository（H2） |
| 空白の扱い | 前後に空白を含む検索語 | C の決定に従う（20 文字 + 空白、21 文字） | Controller |
| 応答の形式 | 日時の形式、NULL 可能な項目（容量）、稼働状況の数値 | 仕様のレスポンス例どおり | 結合 |

## 7. サンプルの進め方から取り入れられる点

| 点 | 内容 |
| --- | --- |
| 実装指示の分割 | 各 step で「このステップだけ実装する」と範囲を明示し、設計書を全文確認させ、単体テストは後工程と明記する |
| レビュー依頼の書き方 | コミットの範囲、参照する仕様、観点、出力要件を指定し、「レビューのみで修正しない」「差分で新たに入った根拠の明確な問題だけ」と絞る |
| レビュー結果の構成 | 良い点、重大度別の指摘（ファイル・行、発生条件、影響、修正方針）、仕様との照合表、総合評価、対応履歴、再レビュー。確認範囲（静的か、実行したか）を明記する |
| 指摘番号の継続 | 設計レビューからの指摘番号を継続し、解消済みの項目を再指摘しない |

これらを今後のレビュー報告書（`docs/review/`）で使う。
