## 1. 目的と背景

- **システム名**: Inventrack（ドローン部品・製品管理システム）[原典 README]
- **目的**: ドローンの部品と製品の在庫管理を効率化し、在庫センターの運営を最適化する [原典]
- **対象業務**: カスタマイズ生産に対応した在庫管理 [原典]
- **顧客**: 2016 年創業の産業用ドローンベンチャー。インフラ点検、農業、救助、物流、警備向けのカスタマイズ生産が主体 [原典]
- **解決したい課題** [原典]
  - 部品の種類が多い（基本 10 種とカスタマイズ部品）ため、部品ごとの在庫レベルの最適化が難しい。
  - 需要予測に基づく調達計画が複雑。
  - 部品の品質・ロット管理が煩雑。
  - 過剰在庫と欠品の両方を避けたい。
  - 顧客別の納期要求に応えたい。

## 2. スコープ

### 2.1 対象機能と現在の状況

| 区分 | 機能 | 原典の状況 | 本リポジトリ（hands_ON）の状況 |
| --- | --- | --- | --- |
| 認証 | 登録、ログイン、トークン更新、ユーザー取得 | 実装済み | 再実装済み |
| カテゴリ管理 | 部品・製品カテゴリの一覧、検索、作成、編集、削除 | 画面仕様とテーブル定義のみ。API 仕様なし | **API と画面を実装済み**（`docs/detailed-design-stocks.md`）。CSV 一括登録は対象外（Q-8） |

| 部品在庫 | 一覧、検索、登録、編集、削除 | 画面仕様とテーブル定義のみ。API 仕様なし | **API と画面を実装済み**。横断検索 API は想定のみ（未実装） |

- 受発注、調達、需要予測、生産計画、ロット・品質管理（課題として挙がっているが、機能の定義が無い）。
- 外部システム連携、モバイル対応（画面仕様は PC を想定）[原典]。

| ID | ルール | 出典 |

## 6. 用語

| 用語 | 意味 |
| --- | --- |
| 在庫センター | 部品・製品を保管する倉庫等の拠点。テーブルは `center_info` |
| 部品 | ドローンの構成要素（フレーム、プロペラ、モーターなど）。基本 10 種とカスタマイズ部品 |
| 製品 | 完成品のドローン（災害用、点検用、配送用、農業用、警備用、撮影用） |
| カテゴリ | 部品・製品の分類。種別で区別する |
| 稼働状況 | センターの稼働中（0）または稼働停止（1） |
| プラットフォーム型生産 | 共通の基本プラットフォームに用途別の部品を追加して作る生産方式 |

## 7. 未決事項・原典の不整合

要件として確定する前に決める事項。「確認先」は私の推奨。

### 7.1 原典の文書間・コード間の不整合（原典のファイルで確認済み）

| ID | 内容 | 該当箇所 | 影響 |
| --- | --- | --- | --- |
| C-1 | 稼働状態は 0 = 稼働中だが、初期データ（Flyway V1）の 3 センターはすべて `1`（稼働停止）。画面仕様は `OPERATIONAL/INACTIVE` という別の表現 | テーブル定義、V1 SQL、画面仕様 | 初期データの誤り、または定義の誤り。画面と API で値の表現が食い違う。**hands_ON ではテーブル定義を優先し、0 に修正済み**（画面の表現は未対応） |
| C-2 | `category_type` はテーブル定義で `'part'/'product'`、V1 SQL の初期データでは `'PARTS'/'PRODUCT'` | テーブル定義、V1 SQL | 部品在庫の画面仕様は `'part'` で絞り込むため、初期データでは該当ゼロになる。**hands_ON では `'part'/'product'` に修正済み（CHECK 制約も追加）** |
| C-3 | ロールの値はテーブル定義の備考に `ROLE_USER, ROLE_ADMIN`、SQL の CHECK 制約は `USER, ADMIN` | テーブル定義、V1 SQL | 保存値の定義が 2 通りある |
| C-4 | 画面は住所を「都道府県（select）、市区町村、番地」に分けるが、テーブルと API は `address` 1 列 | 画面仕様、テーブル定義 | 結合して保存するか、列を分けるかを決める。**仮決定（フロントエンド実装時）**: DB と API は 1 列のまま。画面で結合して送り、編集時は先頭からの簡易判定で分割する（`docs/frontend-centers-design.md` 第 4 章）。列を分ける場合はスキーマ変更と API 契約の変更になるため、承認後に行う |
| C-5 | 製品在庫の画面に「製品コード」があるが、`products_stock_info` に該当列が無い | 画面仕様、テーブル定義 | 列の追加が必要。**解消済み**: `V4__add_product_code.sql` で `product_code VARCHAR(20)`（NOT NULL、一意。DB の制約で保証）を追加。既存の行は `PRD-` + stock_id（6 桁ゼロ埋め）を入れた。**連番ではなく、stock_id の欠番は製品コードにも欠番になる**。新規の行の製品コードは利用者が入力する（自動採番しない）（`docs/detailed-design-stocks.md` 第 5.1 章） |
| C-6 | 画面の文字数上限が、テーブルの桁数と異なる（製品名 20 と 255、在庫説明 50 と 255、カテゴリ説明 50 と 255） | 画面仕様、テーブル定義 | 「テーブル定義が唯一の真実」（copilot-instructions）に従うなら画面側の修正が必要。**在庫・カテゴリの API では DB の桁数（255）を採用**（`docs/detailed-design-stocks.md` 第 7 章） |
| C-7 | 部品在庫の名称は重複禁止だが、ユニーク制約が無い。センターが違う同名品を認めるかも不明 | 画面仕様、テーブル定義 | 重複の判定単位を決める。**仮決定**: 同じセンター内（別のセンターは同名可）。Service の事前照合と DB の一意制約（V5）で保証 |
| C-8 | `post_code` の桁数は 10 で、例の `530-0001` は 8 文字。列名は「保管容量」と「保存容量」が混在 | テーブル定義、API 仕様 | 表記の統一が必要 |
| C-9 | 在庫センター画面の初期ソートが「カテゴリ種別降順、カテゴリ名降順」（カテゴリ画面の複写）。API は `centerId` の降順 | 画面仕様、API 仕様 | 画面の誤記と判断し、API に合わせる。**フロントエンドでも `centerId` の降順を初期値にした** |
| C-10 | カテゴリ画面に「行ごとの操作は表示のみ」と「操作（編集、削除）」の両方が書かれている | 画面仕様 | どちらが正かを決める。**在庫センター画面は「操作（編集、削除）」を表示する実装にした（仮決定）** |
| C-11 | Spring Boot のバージョンが README は 3.4.3、`pom.xml` と copilot-instructions は 3.5.3。API 仕様書のファイル名も `api-spec.md` と `api-interface-spec.md` が混在 | README、pom、copilot-instructions | 文書の更新 |
| C-12 | Flyway と `spring.jpa.hibernate.ddl-auto=update` が同時に有効 | `application.properties` | スキーマの管理主体が 2 つになる。**hands_ON では Flyway に一本化し、`ddl-auto=validate` に変更済み** |
| C-13 | `create_date` と `update_date` の備考が「操作が行われた日時（create_date と一致）」で、更新日時の意味と合わない | テーブル定義 | 記述の修正 |

  - Javadoc と JSDoc を日本語で書く。

- **画面から API への接続** [原典 `next.config.mjs`]: Next.js の `rewrites` が `/api/*` をバックエンドに転送する。ブラウザから見ると同一オリジン。

## 9. 受け入れ基準（在庫センター一覧 API）

| 観点 | 基準 |
| --- | --- |
| 正常系 | 認証済みで `GET /api/v1/centers` が 200 を返し、`data` と `meta` を含む。削除済みは出ない |
| 検索 | センター名、住所は部分一致、稼働状況は完全一致。条件の組み合わせは AND |
| ソート・ページング | 8 項目でソートでき、`page`、`size` に従う。指定がなければ `centerId` の降順、1 ページ 20 件 |
| 入力エラー | `page<1`、`size>100`、不正な `sort`、`order`、`operationalStatus` は 400 |
| 認証・認可 | トークンなしは 401。USER 権限が無ければ 403 |
| テスト | 正常系、異常系、境界値を網羅するユニットテストがある。カバレッジは 80% 以上（原典の JaCoCo 設定） |
